# お役立ち記事の書き方（定期の自動作成用）

Orcaの定期実行（automation「お役立ち記事の作成（月・木）」）は、このファイルに従って1回に1本の記事を書き、本番に公開する。
人が手で書くときも同じルールに従う。

## 1. テーマを選ぶ

- `docs/articles/topics.md` の「未着手」のうち、いちばん上のものを書く。
- 書き終えたら、その行を「公開済み」の表に移し、公開日を入れる。
- 未着手が5件以下になったら、同じ形式で新しいテーマを5件以上、末尾に足す。足すときは次を守る。
  - 情シス代行 → データ活用 → 生成AI活用 → Web制作 の順に並べる。
  - 既存記事（`components/articles/ArticlesIndex.tsx` の `articles`）や公開済みのテーマと、検索意図がかぶらないものにする。
  - 中小企業の経営者・総務担当者が実際に検索しそうな悩みにする。
  - 「プロンプト 書き方」「KPI 決め方」「GA4 使い方」のような大きな検索語は避ける。大手メディアと競うことになり、上位に入りにくい。
    代わりに、具体的な場面の悩み（例：「退職者 Microsoft 365 アカウント 削除」「freee Power BI」）を狙う。
  - Arcleの強み（Microsoft 365・Google Workspaceの運用、Power BI・Tableau、freee、AWS、生成AIの社内導入）が活きるテーマを優先する。

## 2. 上位のページと見比べる

書く前に、狙う検索語で上位に出ているページを読み、記事に入れる項目を決める。読者が当然期待することを落とさず、そのうえでArcleにしか書けないことを足すため。

- `topics.md` の「狙う検索語」の最初の語でWeb検索し、結果の上から記事のページを3つ選ぶ。広告、動画、SNS、Q&Aサイト（知恵袋など）、`arcle.net` は飛ばす。
- 3つとも実際に開いて本文を読む。検索結果の抜粋だけで判断しない。開けないページは飛ばし、次のページを使う。
- 3ページの見出しと、扱っている論点（手順・費用・注意点・比べる観点など）を書き出して、次のように分ける。
  - 3ページすべてにある項目：読者が当然期待するものなので、自分の記事にも入れる。
  - 1ページにしかない項目：読者の悩みの解決に要るかを考え、要るものだけ入れる。
  - どのページにもなく、Arcleが実際に出せるもの：1つ以上足す。たとえば、現場メモ（`topics.md` にある場合だけ）、手順の表やチェックリスト、公式情報で確かめた数字、IT担当者がいない少人数の会社を前提にした判断の基準。3章の「事実の扱い」は、ここでも同じように守る。
- 上位の3ページがすべて、大手メディア、官公庁、メーカーの公式ページで、中小企業向けの具体的な場面に絞っても勝てそうにないときは、そのテーマは書かない。`topics.md` で「未着手」の末尾へ回し、「狙う検索語」の欄に「（上位が大手・公式のため後回し YYYY-MM-DD）」と書き添える。そして、次のテーマで同じように見比べる。
  - 見比べるのは、未着手の上から3テーマまで。3つとも勝てそうにないときは、いちばん上のテーマを書く。その場合は、狙う検索語を、より具体的な場面（会社の規模、使っているツール、困っている状況）に絞り直す。
  - 1章の「大きな検索語は避ける」は、テーマを足すときの決まり。この章は、書く直前に、実際の検索結果でそれを確かめる工程にあたる。
- 他サイトの文章、見出しの言い回し、構成の順番を写さない。見比べるのは「何を扱っているか」だけで、文章と構成は自分で組み立てる。他サイトにある数字や説明は使わず、使うなら公式の情報で確かめ直して、出典にはその公式のページを載せる（他サイトの記事は出典に載せない）。
- 見比べた3ページのURLと、足した「どこにもない項目」は、報告に書く。

## 3. 記事の中身

- 読者：IT担当者がいない中小企業の経営者・総務担当者。専門用語は初出で一言説明する。
- 分量：本文で4,500〜7,000字（check-article の数え方）。見出し（h2）は5〜7個に加え、「まとめ」と「よくある質問（3〜4問）」を入れる。
- 表かチェックリストを最低1つ入れる。手順や判断基準など、読んだあとにすぐ使える形にする。
- 地域名（愛知・東海・一宮など）は `description` にだけ入れる。`title`、本文、`pageTitle`、見出し、FAQには入れない。
  - 記事が狙うのは「やり方・選び方」を調べる検索で、地域名を付けて調べる人はほとんどいない。地域名を付けた依頼の検索（「情シス代行 愛知」など）はサービスページに任せる（記事がサービスページより上に出てしまうため。2026-11-06、2026-11-10）。
- `title` は、狙う検索語を先頭に置き、本文の作りに数があれば「〜の5つの手順」「比べる4つの点」のように数を入れる。数は本文の見出しや表と一致させる（例：手順の見出しが5つなら「5つの手順」）。
- 日付のすぐ下に「この記事の結論」（`<ArticleSummary>`）を置き、記事の答えを3〜4文・150〜200字で先に書く。読む人が最初に答えを知れるようにし、AIの答えにも引用されやすくするため。本文に書いていないことは書かない。
- 「Arcleの現場では」の段落：`docs/articles/topics.md` の「現場メモ」に、その記事の slug のメモがあれば、合う見出しの中に1段落で入れる。「Arcleが支援した会社では、〜でした」のように、メモにあることだけを書き、数字や出来事を足さない。メモがなければこの段落は書かない（作り話の体験談を書かない）。
- 記事の最後（よくある質問のすぐ下）に「出典」（`<ArticleSources>`）を置き、書く前に確かめた公式の情報（メーカーの公式ページ・ヘルプ、官公庁の資料など）を、名前とURLで並べる。開いて中身を確かめたページだけを載せる。
- 事実の扱い
  - 料金、プラン名、機能の有無、法律・制度、サポート期限など、変わりうる事実は書く前にWebで公式情報を確認する。確認できなければ具体的な数字や名前を書かず、「最新の情報は公式サイトで確認」と書く。
  - 統計の数字、調査結果、実在する顧客の事例を作らない。例を出すときは「たとえば」と仮の状況にする。
  - 「必ず」「絶対」「検索順位が上がる」のような保証表現を使わない。
- Arcleの宣伝は、本文中の囲み1つと末尾の「関連サービス」だけにする。囲みの文言は、`components/next/theme.ts` と各サービスページ（`components/next/pages/*Next.tsx`）に書かれている内容の範囲で書く。対応していないサービスや料金を作らない。
- 関連記事には、同じタグの既存記事を1〜2本と記事一覧へのリンクを入れる。
- Arcleは個人事業。自分のことは「Arcle」と書き、「当社」「弊社」「スタッフ」「チーム」など会社や複数人を思わせる言い方をしない。
- 文体は「です・ます」。一文を短くし、箇条書きを使いすぎない。

## 4. ファイルの作り方

既存の記事 `components/articles/ArticleWebCompanyGuide.tsx` を雛形にする（Helmet、JSON-LD 3つ、PageHeader、この記事の結論（`<ArticleSummary service="<key>">…</ArticleSummary>`）、本文、FAQ、出典（`<ArticleSources service="<key>" items={[{ label, url }]}/>`）、関連する支援事例（`<ArticleWorks service="<key>"/>`）、関連記事、関連サービス、著者欄）。関連する支援事例は、記事と同じサービスの事例へのリンクで、事例のページを孤立させないために必ず入れる。

導入文のすぐ下（最初のh2の直前）に目次 `<ArticleToc service="<key>" items={[...]}/>` を必ず入れる。本文の大見出しに上から `id="sec-1"`、`id="sec-2"`…を、よくある質問に `id="faq"` を付け、items に同じ順で `{ id, label }` を書く（label は見出しの先頭の番号を除いた文字）。関連する支援事例・関連記事・関連サービスは目次に入れない。

- ファイル名：`components/articles/Article<英語のPascalCase>.tsx`
- `title`：検索向けのタイトル。地域名を入れない。狙う検索語を先頭に、32字前後。
- `pageTitle`：画面に出す見出し。地域名を入れない。
- `description`：120字前後。地域名を入れてよい。
- `canonical`：`https://www.arcle.net/articles/<slug>`（slugは topics.md のもの）
- `published`：公開日（JST の YYYY-MM-DD）。
- 色のクラスは記事のサービスに合わせる（`text-svc-josys` / `text-svc-data` / `text-svc-ai` / `text-svc-web`）。`services.find((item) => item.key === '<key>')` で取る。

登録する場所は3つ。

1. `App.tsx`：import を記事の import 群の最後に、`<Route path="/articles/<slug>" ...>` を記事の Route 群の最後に足す。
2. `components/articles/ArticlesIndex.tsx`：`articles` 配列の先頭に足す。`title` は pageTitle と同じか短くしたもの（地域名なし）、`tag` は `情シス代行` / `データ活用` / `生成AI` / `Web制作` のどれか。
3. `public/sitemap.xml`：記事のURLを最後の記事の後ろに足す（lastmodは公開日、changefreq monthly、priority 0.7）。`/articles` の lastmod も公開日にする。

## 5. 確認と公開

1. `npm run build` が通ること（prerender まで含む）。
2. `dist/articles/<slug>.html` ができていること。
3. `node scripts/check-article.mjs <slug>` がすべて OK になること（title・description・canonical・h1・字数・地域名・目次・結論・出典・sitemap）。
4. コミットメッセージは1行の日本語（例：「お役立ち記事『〜』を追加」）。Co-Authored-By は入れない。
5. `git push origin HEAD:main` で公開する（Vercelが自動でデプロイする）。
6. プッシュ後、`gh api repos/momonga1192/momonga1192/commits/<sha>/statuses --jq '.[0].state'` が success になるまで数分おきに確認し、`curl -s https://www.arcle.net/articles/<slug>` で公開を確かめる。
7. 失敗したときは、本番に壊れたものを出さないことを優先する。ビルドが通らないものはプッシュしない。
